# 企业级解决方案

> 这里我写了企业级的解决方案，将model封装，作为一个方法来使用，调用方只需要使用模型，不需要关心模型的其他内容，包括模型的选择，模型的错误处理，模型的断链,模型的降级等等问题。

## 错误分类:

看了一下阿里百炼的API，错误信息分的特别细，有几百种。DeepSeek的错误信息根据HTTP状态来区分的。GLM也是根据http状态码来区分的，同时对应有业务码。

不同的厂商针对错误返回的数据结构都不一样，这里统一封装的话就需要每个厂商写一个适配器，从而统一错误数据机构。

根据错误类型，将错误分为几种类型：

- CLIENT
- AUTH
- NETWORK
- SERVICE
- RATE_LIMIT

根据这5种类型，CLIENT和AUTH 属于需要用户操作的，剩下三种都属于是需要重试的。

## 重试与降级的企业级解决方案

假如说第一模型因为某种原因导致重试失败，需要降级。那么问题来了，降级之后是一直都使用第二模型吗？还是说需要等5分钟再试第一模型？还是说需要什么特别的处理？

> 针对以上场景：企业级的做法是需要再一段时间后重试，这样的话就能智能的使用大模型，而非第一模型出错之后一直使用第二模型。所以在重试与降级之后还需要做的以下几个方面

- Per-Provider 熔断器：不是简单的降级跳下一个，而是完全阻断对该厂商的请求
- 半开状态（Half-Open）：熔断后定期放行探测请求，成功则自动恢复
- 可配置阈值：失败次数 / 失败率 / 时间窗口 / 熔断持续时间均可调
- 与降级链解耦：熔断 = 全局不调用该厂商；降级 = 当前链跳到下一个

熔断的本质是第一模型熔断之后，给一个重试的机会，如果正常的话就恢复。
整个熔断逻辑我的理解：当第一模型因为网络错误服务错误以及请求过多导致重试的时候，重试三次之后还是错误，这个时候进入熔断，此时当前模型被标记为OPEN状态，大模型降级为第二模型。假设设置的熔断冷却时间为1分钟，一分钟之后当前模型的状态为半开状态。在1分钟之后的请求之后，监测到第一模型为半开状态就拿第一模型去请求一次，请求成功之后就标记为CLOSED状态，如果还是错误那就标记为OPEN状态。

对于熔断器来说，如果多个模型都被熔断了，那再一段的时间之后 必定有一个模型结束冷却变为半开状态，这个时候拿半开状态的模型去重试。
